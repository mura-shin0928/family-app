# ライフイベント画面：「探す」と「記録」への作り直し

日付: 2026-10-02 / 対象: 旧「手続き」画面（`/procedures`）、タスク画面のクイック入力・行

## 背景と目的

いまは「やること」を登録・更新する場所が2つある（手続き画面の「これから」と、タスク画面）。
どちらを更新すればいいか迷うのが問題。

- **やることの登録・更新はタスクに一本化する。**
- **ライフイベント画面は「探す」と「記録」の2つに絞る。**
  - 探す＝その時期にやること（行政手続き・慣習の行事・準備）をカタログから見つけ、タスクにする。
  - 記録＝いつ何をやったかを子供ごとに残す。タスクで完了すれば自動で入る。

成功の基準:
- どちらで更新するか迷わない。
- ライフイベント画面を開けば「この時期に何があるか」「何をやったか」が分かる。

将来は子供に関係しない制度・手続き・イベント（引っ越し、確定申告、介護など）もここに並べたい。
今回は作らないが、子供専用に見える名前や構造は避ける。

## 決定事項の一覧

| 論点 | 決定 |
|---|---|
| タスク完了と記録 | タスクがライフイベント項目への参照を持ち、完了で自動記録 |
| タスクにした項目の見せ方 | 探すタブに「タスク追加済み」チップを付けて残す |
| 既存の「これから」(`active`) | 移行しない（カタログに戻る） |
| 画面の骨格 | 「探す｜記録」の切り替え（タイムライン型・ハブ型は不採用） |
| 探す対象 | カタログを直接探す。「候補を追加」の手順はなくす |
| 行政／慣習の区別 | なくす（`isGovernment` もバッジも削除） |
| カタログ外の項目 | タスク作成時に「どの子の記録に残すか」を選ぶ |
| 記録の分け方 | 子供ごと・日付順。イベント別には分けない |
| 見送り | なくす |
| 妊活の目安時期 | 出さない（`event_start` 基準を廃止） |
| ページタイトル | タスク / レシピ / ライフイベント |

## 1. カタログ

テンプレ（コード内）と自治体の制度（seido-data-hub）を同じ形に揃える。

```ts
type CatalogItem = {
  key: string;          // 安定した識別子。テンプレは手書きの slug（例 "birth:birth-registration"）、
                        // 制度は "program:<seido-data-hub の id>"。項目名を変えても記録との対応が切れない
  kind: LifeEventKind;  // preconception / pregnancy / birth / nursery / school。探すタブの絞り込み用
  title: string;
  summary: string;      // 一覧に出す一言説明。空なら表示しない
  note: string | null;  // シートに出す詳しい説明
  aliases: string[];    // 検索用の別名
  timing: {
    kind: "deadline" | "around";
    anchor: "birth" | "expected_birth";
    offsetDays: number;
  } | null;
  url: string | null;
};
```

- 既存テンプレ（`default-templates.ts`）は、この型へ機械的に移し替える。
  - `isGovernment` を削除し、`anchorEvent: "event_start"` の項目は `timing: null` にする。
  - 各項目に slug の `key` を振る。`summary` は空、`aliases` は `[]` で始める。
- 自治体の制度は取得時にこの形へ変換する。
  - `kind` は、既存の子の時期での絞り込み（`features/programs/filter`）を流用して割り当てる。
  - `summary` と `aliases` は API にあれば使い、なければ空にする。
- 項目の追加・削除・言い換え、`summary`・`aliases` の記入は**別タスク**（後述）。

## 2. データ

### テーブル `life_event_items`（新設）

「ある子について、家族が手を付けたカタログ項目（またはカタログ外の項目）」を1行で表す。

| 列 | 型 | 備考 |
|---|---|---|
| `id` | uuid | |
| `family_id` | uuid | |
| `child_id` | uuid not null | 将来の家族単位の項目は null 可にして足す |
| `catalog_key` | text null | カタログ外なら null |
| `title` | text not null | 作成時点の項目名。カタログ側を言い換えても記録の表示は変わらない |
| `note` | text null | 記録に残すメモ |
| `status` | text | `in_task` / `done` |
| `done_on` | date null | |
| `created_by` / `created_at` / `updated_at` / `deleted_at` | | 既存テーブルと同じ |

- check 制約：`(status = 'done') = (done_on is not null)`
- 部分ユニーク：`(child_id, catalog_key) where deleted_at is null and catalog_key is not null`
- RLS は既存の family 方式に、`child_id` が同じ家族の子かどうかのチェックを加える。

### `tasks.life_event_item_id`（追加）

uuid null、`life_event_items(id)` への FK。

### 削除

- `life_events` / `life_event_procedures` を drop する。
- `/procedures/programs` ページを削除し、探すタブに統合する。

## 3. 同期ルール

タスクの完了・完了解除・削除に伴う同期は、tasks の DB トリガーで行う（タスクの更新と同じトランザクションで揃えるため）。それ以外は Server Action で行う。

| 操作 | `life_event_items` 側 |
|---|---|
| 探すから「タスクに追加」 | 行を `in_task` で作る（論理削除されていない同じ `catalog_key` の行があれば再利用）＋ その行を参照するタスクを作る |
| タスクのクイック入力で「記録」をオン | `catalog_key = null` の行を `in_task` で作り、タスクから参照する |
| タスクを完了 | `in_task → done`、`done_on = 今日(JST)`（すでに `done` なら何もしない） |
| タスクの完了を外す | `done → in_task`、`done_on = null` |
| タスクを削除 | 行が `in_task` なら論理削除する（カタログ項目は探すに戻る）。`done` なら何もしない |
| 「タスクに追加」の Undo | タスクの削除と同じ |
| 探すから「もうやった」 | 日付を選び、行を `done` で作る（`in_task` の行があれば `done` に更新する。タスクには触らない） |
| 記録から外す | 行を論理削除する。タスクには触らない |
| やった日を直す／メモ | 行を更新する |

## 4. 画面

### ページタイトル

| ルート | 今 | 変更後 |
|---|---|---|
| `/tasks` | 一覧 | タスク |
| `/recipes` | レシピ | レシピ（変更なし） |
| `/procedures` → `/life-events` | 手続き | ライフイベント |

- `/procedures` は削除する（使うのは家族だけなので、リダイレクトは置かない）。
- 下のナビの `aria-label` も同じ名前に揃える。

### ライフイベント画面

上から次の順に並べる。

1. 子供タブ（子が1人なら出さない）
2. 「探す｜記録」の切り替え
3. タブの中身

子供が0人なら、今と同じく家族画面への案内だけを出す。

**探すタブ**
- 検索欄と、絞り込みチップ（いまの時期 / 妊活 / 妊娠 / 出産 / 保育園 / 小学校）を置く。
- **いまの時期**（初期表示）
  - 目安日が「今日の30日前〜90日後」に入る項目を、目安日の順に出す。
  - 目安日は、子の出生日または予定日に `offsetDays` を足して求める。
  - 子に日付がない場合や、時期のない項目は出さない。該当が0件なら、イベントのチップから探すよう案内する。
  - テンプレ側の見出しの下に、基準を示す一行を出す（「いまの時期 ─ 予定日 2026/12/10・妊娠8か月」「いまの時期 ─ 出生日 2026/8/20・生後1か月」）。
- 検索語を入れたら、イベントをまたいで、`title`・`aliases`・`summary` に部分一致するものを出す。
- 検索欄のプレースホルダは「例: 出生届、児童手当」。
- テンプレ側の一覧には「一般的な手続き・行事」の見出しを出し、制度側と出どころを区別する。
- 自治体の制度は、一覧の中で「◯◯市の制度」という区分として出す。
  - 見出しはテンプレ側と同じ強さにし、出典の表記は見出しのすぐ下に出す。
  - 「いまの時期」では最初の5件だけ出し、「すべて見る（N件）」で全件を開く（制度は時期を持たず全件が当たるため）。
  - seido-data-hub は探すタブを開いたときにだけ取得する。
  - 自治体が未設定なら、その区分に設定への案内を出す。
- 各行には、項目名・一言説明・時期を表示する。
  - 行そのものは押せない。操作は行の右端の「＋」に揃え、「＋」で詳細シートを開く。
  - シートには説明・公式ページ・「タスクに追加」「もうやった」を出す。「タスクに追加」は確認ダイアログを開く（タスク名＝項目名、期限＝目安日でプリセットする）。
- 状態の表示
  - `in_task`：「タスク追加済み」チップを付け、「＋」は出さない。
  - `done`：行を薄く表示し、「◯/◯ 記録済み」と添える。

**記録タブ**
- 子供ごとに、`done_on` の新しい順に並べ、月ごとに見出しを付ける。出どころのラベルは出さない。
- 行の「⋯」メニュー
  - やった日を直す
  - メモ
  - 記録から外す
- 記録から外すときは確認ダイアログを出す。文言は、カタログ項目なら「探すに戻ります」、カタログ外なら「記録から消えます」。

### タスク画面

- クイック入力のチップ（期限・買うもの・場所）に「記録」チップを足す。
  - 押すと「どの子の記録に残す？」を選ぶ（子が1人なら即オン）。
  - オンのときの表示は「📝 はるの記録」。
- 行：`life_event_item_id` を持つタスクには「📝 はる」チップを付ける。
- 既存のタスクを後から記録対象にする操作は入れない。

## 5. 移行

migration 1本で行う（マージ後に CI が自動適用する）。

1. `life_event_items` を作り、`tasks.life_event_item_id` を足す。
2. 既存の `life_event_procedures` のうち `status = 'done'` の行を `life_event_items` へ `done` で移す。
   - `title`・`note`・`done_on`・`child_id` を引き継ぐ。
   - `catalog_key` は、旧 `template_key`（`kind:title`）から新しい slug への対応表で変換する。対応しないもの（`legacy`、手で足した項目）は null にする。
3. `active` / `candidate` / `skipped` は移さない（カタログに戻る）。
4. `life_event_procedures` と `life_events` を drop する。

旧「やることに追加」で作られた既存タスクは、参照を持たないので普通のタスクのまま残る。

- テーブル：`life_event_items`、参照：`tasks.life_event_item_id`

## 7. テスト

- **単体**
  - カタログと `life_event_items` の突き合わせ（タスク追加済み／記録済みの判定）
  - いまの時期の絞り込み（範囲の境界、日付なし、時期なし）
  - 検索の一致判定
  - 同期ルールの状態遷移
  - 制度 → `CatalogItem` の変換
- **統合**（CI では動かないのでローカルで実行する）
  - `life_event_items` の RLS（他家族・他家族の子）
  - 部分ユニーク
  - タスク操作との同期

## 範囲外（別タスク）

- **カタログの中身の見直し**
  - 項目の追加・削除・言い換え、`summary`・`aliases` の記入、目安時期の修正。
  - 基準は「ライフイベントに付いて回る、調べないと分からないもの」とする。たとえば「復職のタイミングを考える」は外す。
  - この spec の実装後に行う。
- 子供に関係しない項目（家族単位）。
- 既存のタスクを後から記録対象にする操作。
