# リリースノートの書き方

PR 本文の「リリースノート」と `release-notes.ts` の書き方。ノートは `/release-notes` にそのまま表示され、ログインなしで誰でも読める。リリースの手順は [docs/operations/release.md](../../docs/operations/release.md)。

## 読み手

アプリを使う家族。開発者ではない。更新通知の「更新内容を見る」から開く人が多いので、「自分の使い方に関係があるか」がすぐ分かるように書く。

## 書き方

PR 本文には、下の表のどれかに当てはめた 1 行を書く。

`release-notes.ts` では 1 リリースが 1 項目で、`date` はリリースする日にする。同じ日に 2 回リリースするときは同じ項目に追記する。`items` は次の順に並べる。

| 種類 | 書く内容 | 文末 | 書く数 |
|---|---|---|---|
| 新機能 | どこで何ができるようになったか | 〜できるようになりました。 | 機能ごとに 1 行 |
| 改善 | 何がどう便利になったか | 〜なりました。 | 変更ごとに 1 行 |
| 不具合の修正 | どの画面で何が起きていたか | 〜を修正しました。 | 修正ごとに 1 行 |
| 裏側の修正 | 下の定型文 | | リリースごとに 1 行まで |

### 新機能

場所と、できることを書く。場所は、利用者が画面で見ている名前を使う。

- 良い例: 家族画面のいちばん下から、家族ごと退会できるようになりました。
- 悪い例: 退会機能を追加しました。

機能の使い方が 1 行で伝わらないときは、1 文足してよい。それ以上の説明は書かない。

### 改善と不具合の修正

利用者が気づける変化だけを書く。

- 良い例: タスクの一覧が開くまでの待ち時間を短くしました。
- 良い例: 完了にしたタスクが一覧に残ることがある不具合を修正しました。
- 悪い例: 一覧の取得処理を修正しました。

同じ画面の小さな修正が重なったときは、1 行にまとめてよい。

### 裏側の修正

依存パッケージの更新、CI、リファクタ、ログの調整など、利用者の操作が変わらない変更は個別に書かない。何行分あっても、次の 1 行にまとめる。

```text
内部の修正を行いました。使い方に変わりはありません。
```

速さや安定性が実際に上がったときだけ「動作の安定性を高めました。」と書いてよい。上がっていないのに書かない。

利用者に見える変更と一緒のリリースなら、この 1 行は省く。

## 書かないこと

- 開発の用語: migration、RLS、API、PR の番号、ブランチ名、ライブラリ名
- 外部サービスの名前: 規約やポリシーに関わる変更は除く
- セキュリティの修正の中身: どこがどう弱かったかは書かず、「安全性を高めました。」とだけ書く
- 同じリリースの中で入れて取り消した変更
- 未公開の機能

個人情報に関わる不具合があったときは、ノートで済ませない。利用者への連絡を別に決める。

## リリースのときに集める

未リリース分を `git log origin/release..origin/main --oneline` で見て、各 PR の本文の「リリースノート」を `gh pr view <番号> --json body` で集める。

- 同じ機能の行はまとめる。リリースの前に取り消された変更は省く。
- 「リリースノート」がない PR は差分から種類を判断する。Dependabot の PR は裏側の修正として扱う。
- 判断に迷う変更は、削らずに下書きに残し、PO に確認する。
